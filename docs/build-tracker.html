How a shipment works

  • A shipment is DONE only when its proof has been run on the live DB. Code review is not proof.
  • Every shipment ends with two updates: docs/USER-GUIDE.md and this file, then npm run tracker.
  • Talk the shipment through before building it. No code until the shape is clear.
  • One shipment at a time. Do not start the next until the current one is proven.
  • If a shipment turns out to be two shipments, split it here rather than letting it sprawl.

Go-live means Heledon go-live: the hotel runs end to end without Excel. Sellable means Sellable: any Nigerian hotel or restaurant can buy it and run it. Anywhere means Anywhere: currency, locale, tax, payments and integrations for any market.

Two products, one codebase

The restaurant is a standalone product. A restaurant-only tenant runs the same app with the room and hotel modules switched off via enabled_modules. The guest is the universal customer, so a restaurant customer is just a guest with no stay, and F&B posts to a pay-now sale or a standalone folio tab instead of a room folio. Shipment 6.4 is the moment that becomes true rather than intended.

The books: accounts, mappings and the journal
  • Chart of accounts, seeded for a new tenant the same way categories and units already are, editable
  • Account mappings by role key, 27 keys derived from every place money moves in the code today, not from purchasing
  • A property can override a mapping; without one the group default applies. Two hotels, two tills, one chart
  • Journal entries numbered JE-000001, permanent, never updated, never deleted, reversed only by counter-entry
  • One post_journal function: refuses an unbalanced entry, honours the posting lock, posts once per source document
  • One rounding line, capped at a naira, because weighted-average cost carries four decimals and the books carry two. Nothing else may absorb a difference

1.1h2
Purchases: suppliers, the order, and receiving it
  • Suppliers as real records, one name only: a partial unique index on the lowercased name stops the same supplier existing twice
  • Suppliers carry what paying them will need: tax ID, withholding rate, bank details. Captured now because a column added to an empty table is free and a backfill conversation with a live hotel is not
  • Purchase order as the document, numbered PO-000001 from the counter that already exists
  • Four statuses: draft, ordered, received, cancelled. 'In transit' is a label the screen derives from outstanding lines, so it can never disagree with the data
  • An ordered purchase order is immutable. Reality is recorded against it, never written over it
  • Destination on every line (inventory, asset, expense) legal from day one; only inventory can be received in this shipment
  • Receive on the order itself, same page. Quantity per line, difference against ordered shown live, a reason required before a difference will post
  • Over-receipt allowed on a manager PIN rather than refused, so nobody has to invent numbers
  • Cost difference between what was agreed and what the invoice says, shown live and stored, without a mandatory box people learn to type through
  • One transaction inside the RPC: receipt, receipt lines and stock movements commit together or not at all
  • Supplier activity derived from the documents. No stored balance column, and not called an account until payments give it a second side
  • Quantity field accepts 10*24 and stores 240. Base units only, no conversion factor anywhere
  • Every receipt posts its own journal through the spine, inside the same transaction. No client-side posting, no backfill page
  • The six stock RPCs that already move money post too: opening, adjustment, receipt, write-off, count variance and reversal. Inventory in the books and inventory in the ledger cannot disagree
  • Purchases and Suppliers side by side in the sidebar, filling the slot already sitting there marked soon
  • The check the ERP could never make: the ledger's inventory balance against an independent recomputation from the movements themselves, on its own Accounts tab, with the rounding residue against the stock valuation shown rather than hidden
  • A list of any movement carrying no journal entry, with the reason. An empty reason is the alarm
  • A dated alarm rather than a silenced one: movements written before this property's RPCs began posting carry a recorded reason, so the list reads zero on day one and still fires on a movement written after the wiring with no entry
  • The rounding residue shown beside the number of movements it accumulated over, and every position that has ever been below zero named on the card with the sentence that explains it
Modelled on how purchasing actually runs in Palstro ERP after a read-only investigation of that codebase, then corrected where the ERP's own migration history showed the scars: three overloaded status columns that 068 had to arbitrate; no destination field at all; journals posted client-side after the RPC returned, leaving the GL 50,000 adrift from the subledger until 067 repaired it; a receive screen with no quantity input despite a schema that supports one; two near-identical received-quantity columns; receipt numbers from count(*)+1, which races; and a supplier balance column the code itself does not trust. Two decisions changed after Code's read-only §0. Purchasing was going to post no journals, because the hotel schema has no ledger at all. Lanre overruled that and he was right: Heledon has not gone live, so this is the last moment when wiring the books costs one shipment instead of a reconstruction project. The spine lands first as 1.1h and this shipment posts into it from its first line. And goods in transit is a state of the order rather than a real location, because landing stock out of a transit location needs the transfer RPCs that do not exist until 6.1, and because teaching post_stock_receipt that one non-store location is secretly fine is how a guard rots. Nothing built in 1.1g is wasted: purchasing calls the same receipt RPC, extended additively so a movement can name the order it came from, and direct receipt survives as the cash-and-carry exception. Two corrections came out of the build, both mine. The reconciliation I specified, that the inventory account equals the stock valuation to the kobo, is not always true and should not be: the ledger sums per-movement values each rounded to the kobo while the valuation carries an average at full precision, so 3 at 10.00 plus 1 at 11.11 legitimately disagree by a kobo. Asserting the ledger against an independent recomputation from the movements is both true and stronger. And one deliberate breakage stayed green because the fixture made the right and the wrong answer the same number, valuing a reversal at an average that had not moved since. That is rule 27 from a fourth direction and it now carries a corollary: a fixture where the correct and incorrect computations coincide cannot test either one. 047 followed within the day because the first look at live showed both reconciliation surfaces lying: the alarm list read 8 rather than 0, and the difference read 533,000 out, because Heledon holds build-era movements written before anything posted. Fixed with a recorded fact, gl_wired_at, not a tolerance: code that did not exist cannot have posted. Two fudges were rejected by name in the migration header, ignoring anything older than N days, and borrowing gl_start_date to silence it. 046 also asked the wrong question about negative positions, counting the ones below zero today rather than the ones that have ever been below zero, which are the only ones that explain a divergence and are usually positive again by the time anyone looks. Three checks were raised against 047 afterwards. Two came back clean, and the second of those was retracted after being tested rather than argued: two views that read exactly like a cross-tenant leak turn out to scope themselves in their own WHERE. The third is a real defect and is still open: a movement with no cost basis is NOT absent from the valuation, so a back-dated write-off throws the reconciliation out by the value of the stock written off, and the comment in the migration claims the opposite. Measured at minus 4,000 on a fixture. Nothing is wrong on live today because no such movement exists yet.
 Order 50kg of rice, receive 47kg: the shortfall demands a reason, the ledger moves by exactly 47, the movement names the goods-received note, and re-sending the same request with a changed quantity is refused rather than silently ignored. Kill the transaction halfway and confirm none of it happened. 77 database assertions on a throwaway property inside the transaction, re-run against seven deliberately broken versions of the migration, plus 63 render assertions with five mutations. Palstro-ERP learnings carried in, so we don't repeat them

  • Lock every RPC down. New SECURITY DEFINER functions default-grant EXECUTE to PUBLIC, which includes anon, and an internal auth.uid() IS NOT NULL check null-bypasses for anon. Revoke, grant to authenticated, assert in-migration. This bit the ERP twice, which is why it is shipment 1.3 and not an afterthought.
  • Fail open, never closed. A transient error means "couldn't check", not "closed". A live shop once went dark on a network blip.
  • No full DELETE + INSERT saves. Delta saves with a server-side empty guard. One blind full replace wiped a plan's pages and walled every tenant on it.
  • Gated features default in. A key missing from an allow-list is invisible to everyone.
  • Derive display from what enforces. Hand-typed pricing bullets drifted from the real access config.
  • Don't touch tested code, and visibility is not deletion. A nav link repoint once read as catastrophic data loss.
  • Keep auth machinery off public surfaces. A staff-auth poll on the public storefront looped errors until Sentry 429'd. Applies directly to shipment 10.2.
  • Financial cards must foot and label. Every line visible, no two figures sharing a bare label.
  • Lists must paginate properly. Server pagination, count, page-of-N, jump, page size, filtered totals, export-all.
  • Stock is movement-sourced, never a stored number. Same rule as the folio balance.
  • Imports validate then commit, and stay idempotent on re-upload.
  • Duplicate-name protection. Exact blocked, fuzzy warned, whitespace collapsed.
  • Browser-made xlsx opens read-only where Purview labelling is enforced. Lead with CSV, offer xlsx.
  • Moving-average cost folds by business date, not insertion time.
  • Multi-location from day one. Every movement carries a location_id.
  • Never hardcode infra values. A retired Vercel apex IP once took a live shop down.
  • Review the deliverable against the intent. "Done" is not "matches the spec".
  • Migration trap: TG_OP and OLD cannot be used in a trigger's WHEN clause.
  • Port the design, not the database. Never wire two Supabase projects together.
